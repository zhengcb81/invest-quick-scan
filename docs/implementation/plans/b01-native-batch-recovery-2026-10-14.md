# B01 剩余旧任务的有界批量恢复与验证复用

状态：实施前设计，尚未交付批量CLI或创建批量确认。依据为[首次真实apply](../reviews/W15/b01-native-apply-2026-10-14.md)。这是原恢复主线的操作改进，不增加逐helper审查，也不再重做三包或首次真实确认。

## 边界与目标

当前25个leased、1个已真实结案failed、4个result_ready。首批仅处理25个旧leased的中性结案：14 length、11 known_response_no_accepted_answer；4个已有checkpoint和已结案IQS_01排除。所有主体、问题/字段、原物理响应、费用、lease和幂等键均从真实原件及已派生请求读取，不由LLM补造。

现有原生CLI单项控制不支持把25条请求当一条确认。目标是明确有限清单的一次原生终端审阅，逐项留下真实、可追溯、可幂等接续的确认和决议；费用/模型请求0。首批上限30、实际25，不扩到2000家公司或自动加入新股票池。后续正常收费准入与模型实验仍用原Q13/调度器，不把无费结案许可扩成付费许可。

## 组合接口与兼容规则

- IQS总控只组装原件清单、批次标识及本机操作交接；StockWiki拥有原生终端身份、当前成员/路由/字段权限、预览与确认；StockQA拥有原物理证明、原账本、单项不可变决议及执行。继续复用WorkDecisionOwnerService和QuickScanWorkStore，不复制LLM客户端、账本或路由器。
- 批次新增显式versioned carrier，与现有单项1.0并存。固定item_id、work/attempt、原request SHA、owner scope/manifest与顺序；重复ID/同work冲突/未知字段/未知未来版本拒绝。不能同版加字段使旧客户端悄悄改变解释。
- 本机operator从实际OS令牌读取，模型/request不得指定actor、executable、确认布尔值或批准端口。一次TTY挑战必须展示完整有限范围/每项动作，绑定全批原件摘要和当前owner状态；不能自动填短语。
- 批次记录显式关联逐项引用。若现有rc1形状不能真实表达批量批准来源，开显式新版本/适配；不能伪称每项都有另一次人工单项操作，不能重签旧确认、改旧决议或修改历史原件。
- owner配置只扩到这25个原问题字段和同一真实主体/路线，依据实际原件重核并版本化；不沿用旧隔离clone权限。保留已执行IQS_01的历史批准/决议语义，不把当前权限更新当历史记录损坏。

## 实施顺序

1. 核当前source HEAD/dirty和writer，冻结本轮真实before与25项名单。重查已有端口是否提供可复用批次能力；当前代码只见单项，不假定存在批量flag。继续避开COMPANY-AGENT-01外包根。
2. 定义闭合carrier、per-item结果、批次预览/确认及恢复游标；每项区分prepared/confirmed/recorded/rejected/unknown。非全成不能标整批成功，失败项不从分母消失。
3. 先在隔离副本写下面的反例，再补最小原生批次入口。仍调用原单项证明/决议逻辑，不放松真实owner/lease/原响应/费用检查。不要对真实库做破坏性反例。
4. 复用纯验证：同一操作内可按完整原字节/锁、code/runtime版本和契约版本缓存不可变包校验，复用固定CLI进程或增加明确批量验证入口。不能缓存当前权限、当前主体/anchor、费用可用额、实际批准或把旧hash当身份认证。审批和实际提交前仍重核变化。
5. 原生终端只批准完整有限scope；持久批准/逐项发布要有可恢复语义。磁盘失败/中断后明确已经确认或落账的项，幂等接续不重复API或重复事件；未经实际批准的剩余项不能补成已批准。
6. 统一做一次大节点验证：单元/契约、隔离组合集成和原入口E2E一起核；保留旧单项1.0、控制1.2/目标1.3的回归。通过后再准备原namespace真实批次预览，由用户完成一次真实TTY验收；测试替身不充当这一正例。
7. 用真实批准执行25项，比较原其他5项/4checkpoint/13次预算/原件，核新增逐项事件和sequence。之后再准备有限小样本的retry/comparison与报价；不因结案批量通过授金融gold或直接扫全池。

## 一组必要测试

|层次|要验证的行为|
|---|---|
|单元/契约|数量/字节上限、重复与冲突、字段/顺序/hash绑定、旧版本可读、未知未来拒绝、已结案项排除|
|权限反例|错主体/字段/原响应/路线/lease/actor、caller permission flag、改动policy/member/anchor、过期与撤权均不能取得有效批准；无付费发送|
|集成|混合14 length/11中性诊断，原proof调用计数与纯验证缓存命中可解释；一个坏项不被假装为全批ready|
|中断/恢复|批准前崩溃无批准；批准后部分发布/部分落账如实呈现，接续不重复事件/不重置费用；并发writer变化拒绝或重新预览|
|事件后验|旧事件前缀逐行不变，每个新决议恰有对应原生事件；sqlite_sequence仅按新增事件递增，不能重复本轮父级断言漏算|
|E2E与清理|真实源CLI/serializer在自有临时namespace组合，运行前后外部原件SHA不变；临时库/下载/子进程清完、收据保留；真实owner批准另由实际TTY取得|

单元注入端口/确认器只标synthetic。实际25个“可派生请求”和现有软件绿灯都不等于批量原生确认。成功标准不是测试数，而是有限批准、准确分母、断点接续、原数据/费用保持和可复核的真实入口。
