## 开始一次实施

1. 读取本页、[设计约束](decision-register.md)、[测试策略](test-strategy.md)和[审查与交接](review-and-handoff.md)。遵循用户当前指令与目标仓库AGENTS；本计划不能赋予跨目录权限。
2. 在invest-quick-scan根目录运行下面的只读命令。任务卡是范围和owner边界，不是必须逐张停顿的工作节奏。每次选一个有明确接口的相邻任务组，连续实施其中已具备输入条件的卡；首次从P00开始。不要把整个M0或M3当成一个无边界改动，也不必等每张小卡都单独审查后才继续下一张。
3. 读取该卡列出的资料与目标仓库真实文件；先核实路径、签名、测试入口和工作树，再填写允许修改的具体文件清单。任务里的proposed路径不是现有API。
4. 先把场景变成真实测试：保留输入、精确断言、失败原因、可重现命令。缺失功能应先产生预期失败；纯文档/研究任务采用逐项检查，不制造无意义的红测。实现过程中按需运行快速定向检查；正式验收按稳定的任务组/大节点合并运行。同一批次可以一次验证多条断言，不为每条断言单独起进程或重复产生日志。
5. 只实现卡中步骤。依赖缺失、契约矛盾、需要另一个拥有者写入时，记录阻塞点，转交对应任务；不要写临时客户端、默认分数或自动下载作为替代。
6. 连续完成同一组中已具备接口的任务，不要求每完成一张卡就做全套测试、生成新日志或停下等待审查。组内保存能复现的局部检查结果；到约定的大节点后，一次运行该组必需的定向/集成回归。全仓回归安排在阶段候选稳定后运行；小修复只重跑失败用例及受影响路径。交付变更清单、批次结果、原始日志路径、当前源文件/提交标识、剩余问题和下一里程碑。
7. 在G0—G6或确有跨仓契约、数据库迁移、收费/派发、安全边界变化的大节点安排独立审查。一次审查覆盖同一变更组的多张任务卡，并逐任务记录绑定快照的结论；不为普通小卡单独开审查轮次。评审发现修复后，只复测受影响范围，再在下一个放行节点做一次合并确认；仅高风险缺陷或契约发生变化时才追加独立复审。没有独立审查资源时可继续不依赖该结论的实现工作，但不能越过相应放行门。

实现依赖用于决定接口顺序和最终放行。上游接口/契约已冻结时，下游可连续实现并在`progress.md`标记待验收；对应里程碑关闭前一次性核验依赖闭包、相关case、测试批次和独立审查。跨仓写入权限仍按原授权边界执行。

```powershell
python -X utf8 scripts/implementation_plan.py validate
python -X utf8 scripts/implementation_plan.py list --stage M0
python -X utf8 scripts/implementation_plan.py list --stage M6 --owner stockqa
python -X utf8 scripts/implementation_plan.py show P00
```

这些命令只读取实施计划：不调用模型、不发网络请求、不执行清单里的命令、不写外部项目，也不自动宣布任务或生产测试通过。validate成功只证明清单结构/依赖/引用满足本包规则，不能证明实现正确。

## 单次任务规模

任务卡只有一个目标仓库和一个可审查目标。通常一次完成一个小模块及其测试；遇到实际接口复杂度明显超过卡片边界，拆出子任务和依赖，再继续。不得把新功能塞进相邻卡片，也不为凑文件数做无关重构。

跨仓变更按生产者与消费者分开交付，以版本化契约和交换样例衔接。各仓的代码改动留在各自工作区；当前状态记在`task_plan.md`和`progress.md`，测试批次保留可复现命令、实际结果与清理情况。历史任务回执只作为归档证据，不生成、不刷新，也不作为当前关闭门。company-wiki在本轮路线中为只读来源，不安排新增writer。

## 什么算完成

实现者写“已完成”不是验收。任务卡是可追溯的交付范围，但正式测试/审查按变更组和里程碑执行，不按卡数增加测试轮次：

- 到里程碑关闭时，所需依赖已验收；变更属于冻结范围，没有未登记的契约变更。上游接口已经冻结时，下游实现可连续推进，未验收部分保持未关闭状态。
- 到该组/里程碑验收时，关联case都有实际结果；失败、skip、xfail、未运行分别报告。关键路径不能靠skip放行。
- 测试调用真实目标实现；mock只替代网络/时间等边界，不能mock掉被测决策本身。
- 复现命令、原始结果、实现快照、计划/场景版本一致；审查后有改动则旧审查失效。
- 到达当前阶段放行点时，审查问题已逐条关闭，或明确标为不阻塞且说明依据；涉及错误实体、收费、默认分数、丢任务、越界存储的未解问题不能放行。
- 有适当的恢复/回退说明；迁移和运行任务保留历史与已有有效答案。

验收场景通过`owner_task`明确唯一负责任务，`requires_tasks`表达完整链路所需的前置工作。里程碑批次记录实际执行的测试、结果和实现快照；同一测试运行可以支撑多条相关断言。局部实现通过不代表后续系统集成通过，缺失的生产链路仍按对应G0—G6关口跟踪。

## 阶段放行

| 关口 | 允许继续做什么 | 必需证据 |
|---|---|---|
| G0 | 实现各仓接口 | 契约、归属、版本、正反例审查完成 |
| G1 | 扩大评分样本 | 真实搜索与8分原样传递、null贯穿、搜索/费用回执和接口审查 |
| G2 | 开始批次可靠性验证 | 60家公司校准、可解释规则、恢复观察与可用性审查 |
| G3 | 扩大评分覆盖、开始完整事实题库 | 200家公司运行、中断/预算/租约/导入恢复、备份恢复与端到端审查 |
| G4 | 开启完整事实检索与两个研究技能联动 | 关系检索正反例、范围补扫、池外发现与消费者审查 |
| G5 | 宣布对应阶段交付 | 约2,000家独立公司覆盖报告、运行与事实能力分别披露、运维回退验证 |
| G6 | 宣布完整跨项目交付与一键开启 | G4和G5均已通过；配套安装/实际加载、统一设置、同一启动入口、真实全链与升级回退证据齐备 |

G3通过后评分覆盖可继续扩大，不必等待G4；完整事实能力仍需G4。形成2,000家候选名单不等于启动全部收费任务。真实运行必须沿用用户配置的提供商顺序和预算；缺少配置时完成离线卡，留下准确的待运行批次，不能伪造在线验收。

C07在G0前冻结启动/配套契约；X01—X12补齐公开控制、配置、安装、用户入口和联调。最终G6覆盖所有任务依赖，不能留下其他目录的功能“以后再接”。正常启动不要求运行规划校验器；规划工具与未来产品启动器用途不同。
