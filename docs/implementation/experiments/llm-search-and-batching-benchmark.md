# LLM 搜索交接与多题打包端到端实验

状态：已进入实施计划；实验须等 M1真实搜索/解析门、M3 Q09预算/并发、Q10结果回执和W10隔离导入/ACK入口通过后运行。本文是预注册实验方案，不是实测结论。

## 要回答的问题

1. Brave/Tavily 返回的检索内容怎样进入模型上下文，哪种注入方式让回答更准确且来源可核？供应商原生 `web_search` 工具在有可验证执行回执时作为独立方案比较。
2. 固定30道评分题时，逐题30次调用、逐题并行、每批3/5/10题、30题单批之间，正确性、结构完整率、总时延和总费用有什么取舍？
3. 搜索缓存、模型前缀缓存和应用答案缓存各自能节省多少；哪些输入变化必须使缓存失效？

不能先假设“大prompt更便宜”或“逐题一定更准确”。先做匹配对照，再在满足准确度底线的配置中选择成本/时延Pareto最优方案。

## 样本与固定条件

- 核心样本3家：A股、港股、美股各1家；按本项目已经验收的身份规则选取，优先覆盖一个多挂牌实体和公司/业务表述复杂的样本。用户本轮已授权为该小型实验选样；这不改变或扩充其约2,000家股票池，也不授权其他任务自行选股。若结果受个别公司类型影响，再经预算审查扩到每市场2家，最多6家。
- 每家公司固定同一份已发布题库中的30个可打分题目 ID；冻结module release、question/prompt/rubric hash、公司身份与`analysis_subject_revision`、证券作用层、信息截止时间和语言。不得临时改题或换答案口径。
- 每种方法对每家公司先做一个冷缓存的完整30题区组，测运营中实际单次成本与总耗时；如预算允许，另做预先冻结数量的独立重复区组。只报告实际运行样本数；三家公司各跑一次时按3个公司级观测给出原始值、中位数和范围，不报虚假的稳定p90/统计显著性。单请求p50/p90只有该方法至少有20个同口径请求时才可列出，并明确它们不是独立公司样本。
- 打包对照必须使用相同公司、截止时间、模型与模型revision、temperature/推理档位、来源上下文和问题版本。打包请求逐题返回`question_id/status/score/evidence_refs/rationale`，缺题、重复ID、串题或schema错误整批无效；只能重试准确失败的题目集合。
- 方法比较固定一个当前可用的provider/model，禁止一半实验被拒后悄悄由不同模型回答。若路由器拒绝，保留已发生的费用/attempt；切换顺位时需另开完整匹配区组，旧部分结果不得拼作同组。provider/model的精确身份及实际route均记入结果。
- 随机化每家公司的方法执行顺序；在尽可能短的时间窗完成配对，记录信息日期，避免行情或新闻变化偏袒某个方法。
- 模型是分层变量，不能把M3、MiMo和DeepSeek混在同一方法臂或同一公司的30题中。第一阶段用用户当前配置且真实可用的MiniMax-M3作为锚点，完成同一搜索context下的六种请求策略；第二阶段对每个市场样本仅复跑逐题基线与第一阶段通过正确性门槛的最优打包候选，并分别固定为MiniMax-M3、`mimo-v2.6-flash`、`deepseek-flash`独立区组。某个模型路由/搜索/结构化输出不支持时保留失败并标`unavailable`，不得临时换模型补题。第二阶段若预算不足则报告模型适用范围未定，不把M3上的胜出外推到其他模型。

## 实验分组

### A. 搜索结果交接

先比较检索结果源与注入格式，不同时改变问题打包方式。

1. **外部结构化context**：通过Brave Search与Tavily Search分别检索固定的6类意图（官方公司/产品、经营与财务、市场与竞争、护城河、风险、增长/变化），将返回结果规整为证据清单。
2. **问题级检索context**：在同一公司同一截止点，对预先选定的10道代表题以题目为query分别检索；只把该题最相关的短结果传给模型。它与共享检索包对照检索粒度的质量、调用量和费用。
3. **供应商原生搜索工具（可选）**：仅对明确支持且能提供真实搜索执行回执的model/provider运行；独立报告，不把模型差异误归因于检索器。模型自称已搜索、文本里有URL或只有普通HTTP成功均不构成搜索证明。

给模型的每条证据统一成`source_id/title/publisher/url/published_at/retrieved_at/short_snippet`，把snippet标成不可信外部数据，要求答案引用`source_id`，不执行或服从snippet中的指令。模型只收到需要的题目相关source IDs和短snippet；不下载完整网页/财报，不把原始搜索响应、全文或隐藏推理写入正式数据库/日志。为可复核模型实际看到的材料，只在run专属临时隔离工件中保留**完全等同于实际发送内容、经过截断后的短snippet快照**及其hash：单snippet最多500个Unicode字符，单家公司本轮累计最多30,000字符；超限须减少结果或分轮，不得放宽后存入正文。快照仅保留至G3独立审查完成，随后按可信manifest清理；最终报告只留hash、来源指针/质量标注和计数，不留snippet正文或原始搜索响应。

Brave 的检索context可使用普通搜索结果或LLM Context结果；Tavily的Search返回紧凑`content`和URL，二者均须规整为同一内部schema后再给LLM，不能把厂商不同的响应格式直接混给不同问题。检索器比较用同一批固定意图与相同top-k/长度上限；评价来源相关性、权威性、时间新鲜度、题目覆盖率、无关/重复结果率及结果最终支持回答的比例。B组的共享context选择规则在看LLM回答前冻结：保留两方共同证据并按来源质量盲评排序；有多种可接受context时，对打包结论只作“固定context条件下”的推断，不声称已找到检索器×打包的联合最优。

### B. 多题打包与并行

先从A组冻结一份共享的检索上下文及`question_id -> relevant source_ids`映射，所有方法完全复用这份输入，隔离“如何搜索”与“如何打包提问”的影响。

| 方法 | 30题模型请求数/公司 | 并发 | 用途 |
|---|---:|---:|---|
| P1 逐题顺序 | 30 | 1 | 简单、低串题风险的基准 |
| P2 逐题并行 | 30 | 配置上限4；provider限制更低则降至配置值 | 隔离并行对总耗时/限流的影响 |
| P3 分组 | 10批×3题 | 同一配置上限 | 小批折中 |
| P4 分组 | 6批×5题 | 同一配置上限 | 候选默认打包大小 |
| P5 分组 | 3批×10题 | 同一配置上限 | 较少请求与上下文干扰的权衡 |
| P6 全量单批 | 1批×30题 | 1 | 测试极限压缩；不因请求数最少而预判胜出 |

分批时按题库模块/主题组成相邻问题组，组间问题数平衡，避免把本来有关联的构念随意拆散。P1—P6在回答中都要求按固定ID返回逐题独立JSON对象；组内共同事实可以复用context，但每题必须单独给分、理由、来源和状态。

### C. 缓存与复用

准确度/时延/费用主比较均以**应用答案缓存冷启动**运行；每种方法使用独立run/cache namespace。provider内部prompt cache无法保证关闭时，保留原状态并读取usage hit/miss，不能把未报告的缓存折扣当零成本。

三层缓存不能只在“全部开启”的完整pipeline里跑一次就彼此归因：应用答案缓存命中会短路搜索与模型请求。使用互不共享的隔离cache namespace，并做三个正交小子实验：搜索缓存子实验绕过应用答案缓存但调用真实搜索；provider前缀缓存子实验绕过应用答案缓存、重复相同固定前缀并读取供应商真实usage；应用答案缓存子实验重复完整且完全相同的输入，观察是否零搜索/模型派发。每种缓存都用独立的冷/warm/失效证据，不把上游未执行误报成命中。

分别记录三层：

- **搜索结果缓存**：缓存键含provider、规范化query、辖区/语言、搜索深度、过滤条件、top-k和TTL/搜索版本。同query在有效TTL内预期hit；改变query/filter/locale/top-k/搜索版本或让TTL过期必须miss。打包主比较共用已冻结搜索输入以公平隔离模型调用；另报告真实冷启动完整管线中每种检索策略实际需要的search call/credit。
- **provider前缀缓存**：记录usage返回的cached/uncached input tokens、cache window及prefix hash；相同固定system/module前缀尽量前置，变量题目与公司上下文放在后面；不得根据理论前缀相同推断实际cache hit。改动模型revision或前缀时以usage验证是否失去命中，不用客户端猜测。
- **应用答案缓存**：key至少覆盖analysis_subject_id/revision、question IDs及release/prompt/rubric hash、model/provider resolved revision、信息截止日、语言、search evidence hash、工具配置与生成参数。只要任何影响答案的输入改变就必须miss；只重做被影响的题。绝不可用公司名称或ticker单独作缓存键。

每家公司至少跑：冷启动正式对照；上述三个正交缓存子实验；同输入立即重复的完整pipeline warm命中检查；修改搜索query/过滤条件和修改一个答案材料性hash的独立失效检查。完整pipeline的warm重复应为0模型/搜索请求且完整复用相同不可变答案；失效检查只重做受影响搜索键/题目。过期TTL路径在小样本另测，不混入冷启动精度。provider端缓存清理/禁用若不受API支持就明确视为不可控：按公司和方法平衡执行顺序，逐请求保留实际cache usage；没有usage回执则按未命中价格保守核算，不从运行顺序推断cache收益。

若将要发布“Brave/Tavily + 某一打包大小”的联合默认，追加小型2×2交叉区组：两个候选检索context × 逐题基线/候选打包策略，在相同题目和模型上各跑同样三家公司。未完成交叉区组时只能分别报告检索器结果和固定context下的打包结果，不宣称二者组合已实证最优。

## 预注册正确性门槛

阈值必须在任何候选方法输出解盲前固定在run manifest；执行者不能看结果后移动门槛。对90个“公司×题目”建立答案基准：两名不参与调用编排的评审者只看冻结题意、评分锚点和独立来源证据，先判定可评分/应为unknown并独立打分；分差超过1分或对关键事实判断不一致，由第三方/用户在解盲前裁决。原始标签、分歧和裁决均留痕。

一个方法通过质量门槛须同时满足：

1. 30题精确ID覆盖率100%，schema有效；仅允许对准确缺失/无效题作一次有界修复，所有原始失败attempt仍纳入费用/完成率。对基准认为可评分的项目，有效1—10分覆盖率至少95%；基准认为应unknown的项目不得强填数值。
2. 非关键事实主张source support率至少90%；每个“公司×方法”按冻结seed分层抽取至少`max(10个题目, 每个入选模块2题)`个不同题目，覆盖本次所有入选模块，并审查这些回答中的全部事实主张；跨三家公司每方法至少审查30条非关键事实主张，若可用主张少于30则审查全部并将support判定标为`inconclusive`。所有critical claim（公司/证券身份、财务数值、重大诉讼/监管/流动性风险）逐条复核，不能留有未解决的重大错误或无来源断言。抽样题ID与seed须在解盲前冻结。
3. 与独立裁决分数相比，MAE不高于0.75分，且可评分项目至少90%落在±1分以内；相对逐题顺序基线，MAE最多差0.25分、source support率最多低5个百分点、gold可评分题有效分覆盖率最多低5个百分点。unknown项目不进入MAE，但必须单独报告比例和原因。

若评分gold本身未完成双人盲评/裁决、critical claims没有逐条复核，或样本数不足以满足预注册抽样下限，则该方法的正确性结论为`inconclusive`，不可进入“胜出”Pareto集。评审者须在看到候选标签前确认gold和manifest已锁定。

## 正确性、耗时、价格及判胜规则

- **正确性**：执行上面的冻结门槛；另报告完全一致率、±1分一致率、MAE、方向偏差、unknown率、claim support抽样分母/分子、过期/冲突来源和critical errors。模型自评不能充当金标准。
- **耗时**：从公司级run启动至30题结果可用的端到端wall time（包含排队、搜索、模型、解析和受控重试）；逐公司报告每个方法的原始总时长、阶段时长与有效答案吞吐。三家公司×单轮只能给中位数/范围，不给p90或显著性结论；只有至少20个同口径完整run才计算run级p50/p90。单请求分位数另列请求数，不能替代完整run耗时。
- **费用**：每公司完整30题费用与每个可用答案费用，分列搜索API/credits、模型输入/输出token、重试/失败attempt和无法确认的预留；记录实际usage及实际扣费。成本单列冷、温缓存结果，不将provider已收取的失败请求漏算。
- **跨模型价格比较**：对按量模型使用执行日厂商价目、响应`usage`中的input/output与cached token计量，并按实际地区/时段计价；按量账单与套餐消耗不混成一个数字。对MiniMax Token Plan同时报告本轮新增现金支出（订阅已支付时通常为0，但额外积分/充值另列）、套餐资源quota净变化、额度拒绝/等待和每个有效答案占用的quota；只有账户/响应能够把本run的quota增量可靠归因时才折算套餐资源用量，不将月套餐价格硬摊成伪造的边际单价。如用户另选普通MiniMax Open Platform API key，则作为另一个独立M3计费区组，按公开/账户按量单价核算，不和Token Plan混合。
- **MiniMax Token Plan**：记录套餐档位、API key类型、run前后5小时/周窗口额度快照、请求/拒绝数、token usage以及额外积分/按量账单。分别报告增量现金支出、套餐/积分额度消耗和可计算时的摊销成本；若没有逐run扣费或可归因quota，则明示“不可精确摊分”，不能虚构每题单价。额度拒绝及等待重置也计入可用性/时延。
- **胜出**：先过质量门槛（100%精确题目ID覆盖，critical claim不得出现未修复的重大错误，schema错误不得进入正式分；blind claim support与评分误差不得劣于逐题基线超过预注册容忍度），再形成正确性—耗时—价格Pareto前沿。若一种方法在精度门槛内同时更快且更便宜则采用；否则给出Pareto选项及业务取舍，不以单一加权总分掩盖质量下降。门槛和模型价格快照须在看结果前写入run manifest。

统计样本只有3家时，结论标作pilot而不是普遍定律。若三个市场或任一方法结果分歧，按预先规则扩展到每市场第2家，复跑胜出方案、逐题基线和造成分歧的候选方案。

## 价格快照与计价纪律

在执行日重新读取官方价表并保存URL、访问UTC时间、地区、币种、计价模式、缓存命中价、模型/端点revision及可复现页面hash；本节价格只作实验计划期估计，不是当前运行配置。已查到的官方说明：

- Brave Search页面公布Search $5/1,000 requests，另有LLM Context端点；执行日重新确认对应账户计划与可计价请求数。
- Tavily官方文档为按credit计价：Basic Search 1 credit、Advanced Search 2 credits；目前PAYG标价$0.008/credit，免费配额也需记录是否实际被消耗。
- MiMo-V2.6-Flash按量公开价（每百万token）目前为：中国区输入缓存命中¥0.02、未命中¥1.00、输出¥2.00；海外区分别为$0.0028、$0.14、$0.28。MiMo联网搜索/解析另计：中国区¥16/1,000次，海外区$5/1,000次。官方文档称搜索内容会附加到prompt，因而还会产生模型输入token；一轮可按`max_keyword`并行多词，不能把一次模型调用等同于一次搜索。
- MiniMax M3 Token Plan是套餐/共享额度，不按普通API的逐token公开单价计费。官方套餐页当前展示Plus/Max/Ultra约¥49/¥119/¥469每月，并以约6亿/18亿/71亿个M3 token月用量作参考；文本、图像、语音（及部分套餐的视频）共享资源，且有5小时、周窗口和动态限流。实验必须记录实际账户套餐、run前后quota、用量/拒绝和额外积分或按量账单。套餐标称吞吐只是官方估算，不得把月费机械除以标称token或题数后称作本次边际成本。
