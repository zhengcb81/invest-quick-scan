# Long native search vs work lease — read-only diagnosis and bounded fix

No live request, process, work lease, clock, key, model answer body or database was changed/read for this diagnosis. Root supplied the actual public-state facts: MSFT physical pack `PACK_BUDGET_afb85fd…` sent at 15:04:38 and completed about 15:15:11 (about 633 seconds); the two 600-second claims expired earlier at 15:13:51/57. The physical original settled with HTTP 200; both logical work items became uncertain and no new checkpoint was permitted. These actual timings were supplied by root rather than independently reconstructed from a production store here.

The source confirms the cause. `src/providers/llm_client.py:1585` uses non-stream `requests` `session.post(..., timeout=self.timeout)` and only proceeds after the complete body is read. That timeout is an idle read/connect limit, not a total wall-time deadline, so periodic heartbeat traffic can keep a 300-second configured request alive longer than 600 seconds. Provider `timeout` is loaded from existing provider configuration (`base_llm_provider.py`, `llm_config.py:get_timeout`), but work claims independently use `QuickScanWorkLifecycle(lease_seconds=600)`; the public runner constructs that lifecycle without forwarding a configurable lease value.

The fencing and money paths are deliberately separate. The original pack journal `record` checks every original lease. If one is expired, it records the original late response, fences the logical members to uncertain, and still records the one physical budget outcome using the actual response and actual cost. `quick_scan_work_transport.record_response` raises `QuickScanWorkUncertainError` for the uncertain pack. The corresponding existing transport test, `test_late_success_preserves_one_physical_receipt_and_cost_but_no_answers`, already asserts one settled physical fee and no checkpoints for late members. This behavior must remain unchanged for old/expired work; a response arriving late is not permission to extend a lease or resend it.

The actual production CLI is `main_with_llm.py` (the other `main.py` and module CLI are legacy interfaces). It already uses explicit option forwarding into `LLMRunner.run` → `_run_single_company` → `QuickScanWorkLifecycle`. The minimal future-only fix is an optional `--work-lease-seconds`, default 600, strict positive finite numeric bound at 86400 and bool/NaN/inf rejection, with validation before reading input/claiming. Forward it into the existing constructor and record a plain execution log summary; preserve the strict C06 and `.scope.json` document formats. Root will separately set newly prepared IQS launch bundles to 3600 and keep original authorization checks. Existing workers and leases are unchanged.

The minimum verification is public CLI default/explicit/invalid forwarding plus actual SDK/fake HTTP/temporary SQLite logical delays: 600-second lease with a 650-second synthetic completion remains uncertain and settles once; 1800-second lease accepts the same completion and saves a valid standard checkpoint; a completion after 1800 is again uncertain, settled once, and never automatically repeated. Test clocks are injected only into disposable store/fake SDK instances; there is no sleep, system clock change or real work modification.

A genuine total wall-time deadline is a separate feature. Increasing the existing request `timeout` or reusing a between-dispatch time cap does not implement it. A future deadline must interrupt/close the actual request body read, preserve unknown outcome and reservations as appropriate, and never imply remote cancellation or automatically retry another model. No pseudo hard-wall timeout or heartbeat change is part of this bounded fix.
