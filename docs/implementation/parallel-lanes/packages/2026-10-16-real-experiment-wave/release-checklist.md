## 总控发布（整组一次）

1. 读取source-requests.json，逐条核root存在/文件存在/原相对路径合规，将清单准确原字节冻结至固定inputs根；清单没有通配符。先核实际六仓HEAD与package1.0.1/六包报告一致，尤其EVID最终af0bdea而非早期source-commits中的中间commit。若不一致，报告/显式重登记，不临时追latest或搬旧source快照充新签收。输入锁记录真实HEAD及每文件rawSHA/bytes；相同文件可只存一次，由consumers声明权限，不复制秘密/预算DB/隐藏思考。锁内package文档与harness发出的卡片hash一致。
2. 检查3根均不存在且互不祖先/后代、不是IQS或任一旧Lab内子目录；记录UTC、resolved规范化根、exists与路径交叠负例。不要创建外部Lab。工人开工再次检查是必要race防护。
3. 做无key/禁网/专属tmp的发布校验：原inputs逐SHA；搬迁inputs正例；删必需文件/改1byte/重复路径/未知锁版本/Windows大小写重复/外跳或junction反例拒绝；消费者子集携带可独立验证，缺别包consumer文件不误拒。锁内根与卡片/root/默认snapshot一致。卡片本地链接全存在；JSON模板可解析但status明确template，不伪造实际测试。
4. 独立整包审查只看这一个发布节点：任务不重复、无跨新包依赖、单卡自含配套、双cutoff/身份/参考部分性/未知费用/真值边界/只读UI/CLI/测试/清理/交接完整。一般问题直接修。检查后冻结新最终hash，不静默改原发布锁。
5. 发布回执写实际检查命令/UTC/结果/总文件数bytes/hash、未执行项目和清理；保留原input，清理自己测试复制根并核剩余0。发出卡片后标dispatched及writer，不能自动派发/发消息或创建新chat。准备验证不是三个候选软件测试通过，也不是金融/生产门通过。
