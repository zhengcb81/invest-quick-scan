# IQS 故障根因与回归证据

1. 原准备异常先于工作锁写入运行诊断，旧 GET 只检查进程去留，随后把原异常替换为自己生成的未知发生记录。采用原 job、attempt 和阶段定位诊断。进程外监督器的关联号仍进入 F4，同一监督器下的各原作业各有独立发生记录。
2. 真实准备子进程在返回主进程之前也可能写出原异常。仅在 IQS 自己的子进程携带本仓原 job/attempt，上游调用只收到公开的反馈关联号。站点、子进程和 F4 公开冷读都引用原诊断。
3. 批协调原因以前只连到进程内存。已有批记录承载当前协调 attempt，错误仍沿既有诊断保存。主动恢复按该 owner 的既有业务记录判断，并为新的协调 attempt 建立独立诊断位置。
4. 计划 CLI 和初次配置初始化缺少统一错误入口，成功检查没有同关联号的连续阶段。正常业务数据和安全检查点分别写出，失败保留结构化因果链。原始参数、配置值、异常正文和模型密钥不进入安全日志。用原 job/attempt 或 F4 run/attempt 都可以冷读对应阶段。轮转日志缺行时现有原诊断仍可按引用读取。
5. 生产答案装配曾把本仓 `scripts` 永久加入 `sys.path`。当前实现取得 owner 公布的资源 DTO，在本仓公开验证器中消费。工作台的文件锁也移经 foundation 公开接口，provider 只依赖独立诊断接口。边界测试验证延迟 schema 导出的实际归属，修正将公开方法返回的普通数据误判作私域实例的问题，并保留私域访问的拒绝反例。

历史记录只在拥有原关联键或原诊断引用时能对应到具体异常。已有批协调历史若缺少当时的 attempt 指针，只能凭原诊断引用冷读，不能从最新错误猜测因果。新记录在准备和批协调启动前已有原归属。本整改验证的是所列风险入口，没有重新部署已安装的技能或改动在途站点。
