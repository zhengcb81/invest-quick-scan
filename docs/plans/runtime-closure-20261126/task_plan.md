# IQS 运行记录与恢复整改

冻结基线 `e0ad75760ff14ce135a7857b090fda9b4663c92f`。对照总控 S1–S5 独审的 IQS 报告和运行生命周期约定。IQS 负责本仓准备、批协调及检查入口。向外部 owner 传递既有公开关联号，原下载、模型请求、费用和研究结果由各自 owner 保存。

| 阶段 | 实施 | 验收 |
| --- | --- | --- |
| S1 和 S2 | 通过实际准备 POST 持有工作锁并强停进程。按原 job 和 attempt 定位属主已保存的诊断。批协调在启动前固定 attempt。 | 新进程通过实际 GET 和公开诊断 CLI 冷读原异常。重复 GET 和提交原预览均只附着原 job。没有保存原原因时如实显示未知。诊断已落盘而投递失败时仍可定位原异常。 |
| S2 | 准备、已存扫描检查及计划 CLI 使用共同的安全运行轨迹。配置拒绝在 owner 装配前保存。 | UTC、阶段、状态、当前实现版本、安全引用和时长可按 run/attempt 冷读。正常 stdout 和退出状态保持兼容。 |
| S3 和 S4 | 生产答案验证使用已约定的资源协议，移除进程全局导入路径变动。日常测试收集经过复现的强停和边界用例。 | 已冻结资源通过同一个公开 port，模块路径隔离规则覆盖普通与延迟导出。Windows 实测强停，Ubuntu 日常组收集相同用例。 |
| S5 | 审查冻结候选以及跨进程诊断携带。 | 由独立 reviewer 复跑 [交接说明](handoff.md) 的指令，根据结果提交本仓并更新总控。 |

运行场景使用独立目录中的离线替身和既有测试夹具。诊断介质和代码升级不触发重新准备、下载、模型请求或付费。
