# 大股票池维护、接续扫描、模型切换与研究联动

日期：2026-09-21。状态：待实施设计。本文件细化并更新[总体设计](stock-pool-design.md)中的运维部分；不表示真实名单、数据库、服务或跨技能接入已经建立。本轮只修改规划文档，不调用收费模型、不修改外部项目、不下载公司文档。

2026-09-22补充：首次/持续入口、自动准入、两库权威及三维比较以[全局契约](system-contract.md)统一；不是只有手工准入。

## 1. 推荐形态：小工具管理名单，既有skill负责编排

建议不另建一个重型“股票池投资分析skill”。名单的导入、增删、去重、版本、状态和查询应由确定性工具完成；用户通过invest-quick-scan或StockWiki页面调用它。只有以后需要独立的周期性选股方法与复盘工作流，才考虑加一个薄的交互skill，仍复用同一工具。

推荐分工：StockWiki拥有名单与轻量画像的本地CLI/查询接口；invest-quick-scan定义问什么、如何路由与解释；StockQA负责真正发问、按模型优先级执行、费用、缓存与接续任务。名单工具不读取API密钥，不自行调用LLM，不采集公司文档。

目标明确为**约2,000家独立上市公司**，多地上市只算一家公司。A/H/美股各600—800作为市场覆盖软目标：分别报告独立公司总数、各市场覆盖公司数、挂牌证券数和多地上市重叠数。重叠不能重复凑够2,000；需要时从覆盖不足的细分行业补位。用户临时加到2,003家也无须自动挤出其他公司。

## 2. 如何产生初始名单

### 2.1 先有真实证券主档，再做入池选择

优先复用company-wiki已有经核验证券主档，也支持用户导出清单或现有工具的版本化快照。主档负责“它是谁、在哪里上市、是什么证券”；不要求这些公司已经有资料文件夹。

可核对的官方入口包括[上交所股票列表](https://www.sse.com.cn/assortment/stock/)、[深交所公司列表](https://www.szse.cn/market/stock/company/)、[HKEX证券列表](https://www.hkex.com.hk/Services/Trading/Securities/Securities-Lists?sc_lang=en)和[Nasdaq Trader证券目录定义](https://www.nasdaqtrader.com/Trader.aspx?id=SymbolDirDefs)。A股范围是否含北交所由配置明确，启用前验证对应主档覆盖；不能把未覆盖默认为没有候选。美股范围明确交易所、ADR、OTC等，不能把所有代码当成普通股；Nasdaq目录本身区分ETF与测试证券。

证券主档/指数成分导入属于对象管理，不是公司画像采集。公司评分与业务事实仍通过StockQA联网问答形成。初建所用市值/流动性等资料如已有合法可用快照可用于排序；没有则报告缺失，先用现成成分名单与行业分层，不为建池另造行情系统，也不让LLM凭记忆编造数千个代码或市值。

### 2.2 分层构建，避免大市值与当前盈利偏差

初始建议比例只是可调的起点，去重后再分配名额：

| 层 | 示例比例/数量 | 选择依据 |
|---|---|---|
| 广覆盖 | 60% / 约1,200家 | 各市场、主要行业、适当规模与流动性的代表公司；指数成分是种子，不是唯一标准 |
| 细分补盲 | 25% / 约500家 | 细分产品、关键材料/设备/服务、小行业龙头和容易被大类行业掩盖的公司 |
| 变化与特殊情形 | 15% / 约300家 | 周期低谷、经营修复、转型、新商业化和其他值得研究但当前指标不漂亮的公司 |

用户指定公司优先保留，可占相应层名额，也可暂时超出总目标。设行业/规模分布检查和最大集中度提示，不强行让所有行业一样多。不能把净利润为正、高ROE或高快扫质量分作为进入大池的必要条件，否则恢复观察和新产业研究会在起点就失去对象。

操作顺序：导入证券候选 → 证券类型和上市状态校验 → 跨挂牌实体去重 → 按市场/行业分层 → 用LLM针对覆盖空白提出少量候选 → 每个提名回查真实身份 → 形成带理由的初始名单。LLM负责补盲提名，不拥有最终证券身份事实。初次快扫后发现行业标签错误或代表性不足，再作名单修订，不循环依赖“先给全市场打分才能入池”。

每层内部先纳入用户固定成员，再按已配置的市场/行业缺口、种子名单等级及可用规模/流动性指标排序；同分用稳定entity_id排序。候选快照、规则、缺失标记和每次入选理由一同保存，使同样输入能重建同一名单。没有可靠行业标签的候选先进入待分类组，不能由名字强配行业。补盲提问由skill经StockQA执行，名单小工具本身不调用LLM。

主档不明、材料不足、流动性弱、风险警示分别留标记；是否纳入及扫描优先级是配置，不默认永久删除。候选不足时报告空缺，不能用低质量或错误标的强行凑数。

### 2.3 用户日常增删应很简单

拟提供以下能力，名称为接口设计而非现有命令：

| 操作 | 行为 |
|---|---|
| universe.import / preview / apply | 导入CSV/JSONL，显示新增、已存在、跨挂牌合并与歧义；批量应用产生新版本 |
| universe.add | 输入交易所+代码或公司名；身份唯一则加入并默认manual_pin，歧义只询问该对象 |
| universe.add_security | 给已有实体关联另一挂牌；复用经营画像，证券字段另列 |
| universe.remove / restore | 逻辑移出/恢复，不删除历史答案或过去入池理由 |
| universe.pin / unpin | 控制自动建议调整时是否保留；pin不等于高分或无风险 |
| universe.list / diff / explain | 看列表、版本差异与为什么入池/暂不扫描 |
| universe.nominate / evaluate / apply-auto | 提名后按已保存propose_only/auto_admit_verified策略核实，符合身份/范围/配额可自动入池 |

用户明确说“把某代码加入大池”即可执行唯一身份的加入，不再要求重复确认；批量预览是工具能力，不是每次增删的强制审批。移除、退市及停止覆盖的历史均保留。单一挂牌退市而同一实体其他挂牌仍有效时，不误停整个公司。

成员记录至少包括entity_id、security_ids、加入来源/理由、加入时间、manual_pin、优先级、active、scan_enabled和变更记录。上市资料状态、长期成员状态、当前白名单状态分开，不因分数下降自动退出大名单。

名单建议半年复盘，用户随时增补；已知退市/更名等身份变化可定向维护，不需要每天重建全名单。本轮不创建计划任务。

## 3. “扫描所有公司”应实现为持久化待办，而非一个长对话

### 3.1 两种运行需求

- **全池补齐/刷新**：对所有active且scan_enabled的独立公司计算本次缺失或过期项。最终覆盖全池，而不是永远只扫描最高分或近期热门公司。
- **定向补扫**：用户或研究技能指定公司、分部和字段，只问所需缺口，复用相同的队列、预算和结果库。

同一公司多挂牌共用经营问题；价格、股类权利、ADR比例等具有证券差异的题另按证券处理。单家公司本次缺少20个问题，不意味着下次应重新回答全部24题。

### 3.2 新鲜度是字段级可用性

已有答案可复用，必须同时满足：对象/作用层正确，题目与锚点口径兼容，业务分类未发生影响该题的变化，实际信息日期满足要求，没有已知新事件使它失效，检查等级足够，且没有待解决矛盾。

skill提供题目语义、适用性和默认时效策略；StockWiki根据其权威观察库返回fresh/missing/stale及原因，生成可审查的缺口计划；StockQA执行这些逻辑待办并负责接续。执行器不得仅凭自己的缓存命中就把过期答案判成新鲜。

初始有效期建议，试点后可调：

| 字段组 | 默认最长复用窗口 | 提前失效条件 |
|---|---|---|
| 身份/路由、业务结构与优势 | 180天 | 重组、业务出售、主要产品/客户结构改变等已知事件 |
| 财务、成长与资本回报 | 90天 | 已知新一期结果发布，或数据期间不再满足查询要求 |
| 关键资金、治理与重大风险 | 30天 | 已知融资、违约、审计/治理事件 |
| 活跃恢复观察的催化与里程碑 | 14—30天 | 到达待验证节点、关键假设被证伪 |
| 下一阶段设备/材料/应用关系 | 180天 | 业务关系终止或发生可知变化 |
| 报价与当前估值 | 按需，报价通常要求当日/最近交易日 | 查询指定日期或证券发生变化；无可靠报价则unknown |

TTL只是上限，不证明资料足够新。没有事件流时不能宣称实时发现全部变更；可以在已授权扫描中做简短联网更新检查，仍由StockQA执行。

必须区分`answered_at`、`information_as_of`、`source_period`、`imported_at`、`checked_at`和`valid_until`。重新导入、失败重试、换一个汇总日期都不刷新答案信息时间。“最近问过但不知道”可以有较短的再次尝试间隔，防止每次重复收费，但它是deferred_unknown，不是fresh有效分数。

`latest`模式允许复用窗口内的历史观察，保留原日期；不能因为今天的as_of不同就重问全池。严格历史时点查询则另行限制可得信息，今天回溯的LLM回答不能假装当时已知。

### 3.3 运行与接续的具体过程

1. 读取名单版本，解析实体，读取已存在的画像和运行任务；身份歧义只挂起对应公司。
2. 找出可复用、缺失、过期、需复核和重试冷却中的字段；缺路由先问路由，再按有效分类生成具体问题。
3. 创建或复用同一逻辑待办，向StockQA提交扫描清单；不在聊天上下文中保存唯一进度。
4. 每完成一道题就持久化结果；使用question pack时按题校验，成功题保留，只补失败或缺失题。
5. 达到本次公司/请求/金额/时间上限即停止派发，妥善记录正在进行的请求和剩余待办。
6. 下次“继续扫描大池”从未完成任务接续，并检查新增成员与新到期字段；无需用户记住扫描到哪个股票代码。

每轮冻结本轮的universe_version、题库/规则版本和默认模型策略；新增成员进入增量待办，不使旧轮次推倒重来。长期未完成的普通公司应有公平调度份额，不能被不断新增的主题热点饿死。推荐保留部分容量用于首次覆盖和最久未更新对象，同时优先处理用户新增、关键风险及正在研究的缺口。

“本轮完成”和“所有评分都有结论”分别统计：有些公司可能已问完但仍unknown。报告应列总实体数、全部可复用、部分补扫、已完成有效、已尝试但缺证据、待执行、延后/失败及总费用；题目数和证券层任务另列，不混成一个成功率。

### 3.4 断点、去重与中断

待办最小单位是entity/security作用层下的一道逻辑题。其唯一键包括对象、题目语义/锚点版本、实质路由版本和一次刷新代次；再次启动任务不会仅因run_id不同就创建同一项。强制刷新是显式新代次。

旧答案通过原始observation_id在数据集中复用，不更改原题面、原as_of或来源，也不塞入新题面冒充刚回答。题库新增3题只补3题；题义变化只使受影响字段失效；改变白名单阈值只重新筛选，不花费LLM重新回答。

建议执行状态为queued、running、retry_wait、result_ready、delivered、needs_attention、cancelled。unknown属于答案状态，不等于执行异常；预算停止或所有模型不可用是运行原因，保留待办。

StockQA对running使用领取租约和可恢复检查点。进程崩溃后先检查是否已有结果/请求回执，再决定重试；外部提供商不支持幂等时不能承诺绝不重复收费。请求已发出但结果不明要记录outcome_uncertain、保留费用预留，优先查询已有回执，再作有上限的重试。

结果先写StockQA自身的轻量outbox/交换包，再由StockWiki导入并回执；导入使用唯一键与hash防重。如果模型已答完而导入失败，下次仅重试导入。两个项目不共享可写数据库，不依赖跨仓事务，也不直接互写内部文件。

## 4. 用户指定模型优先级，StockQA统一执行

已核实StockQA的`src/utils/llm_integration.py`有ProviderCascade、有序providers、失败计数、可选健康检查，以及缓存和token统计。方案是扩展并接入它，验证生产调用链，不在本skill重写客户端或创建第二套fallback。

用户维护有序的提供商/模型配置，例如A→B→C。正常题目先选顺序中第一个已启用、支持真实搜索和目标回复格式、且不在故障冷却中的模型；成功即停止，不默认让几个模型全部回答一遍。

模型策略放在StockQA，由其配置入口修改；StockWiki可显示并调用该入口，但不保存第二份可变模型配置。每次运行记录策略版本和最终使用的提供商/模型。默认调整作用于新运行；如果用户要求当前运行立即生效，则在派发边界记录一次显式策略版本切换，只影响未派发待办。已完成答案不因此自动重跑，也不静默改写旧运行的策略快照。

| 情况 | 建议处理 |
|---|---|
| 限流、服务繁忙、网络超时、5xx | 每模型有限重试，较长Retry-After进入冷却并尝试后续模型；不让全部公司反复碰撞同一故障 |
| 模型账号额度耗尽或认证失败 | 暂时标不可用，记录原因，尝试已获授权的下一模型；用户总预算到顶则停止全部派发 |
| 模型不支持搜索/所需输出 | 能力预检跳过并解释，不退回未联网记忆评分 |
| 单次结构输出不合法 | 限定一次格式修复；仍不合法可换后续模型，保留失败记录 |
| 客户端参数/配置本身错误 | 修复请求或标需处理，不把同一个坏请求盲目遍历所有提供商 |
| 正常回答低分、负面判断或证据不足 | 不作为模型失败，不为了拿到高分而切换；补证/独立复核是另一个有预算的任务 |
| 内容安全/访问限制拒绝 | 记录并检查原因，不能用换模型绕过限制；与普通服务拒绝区分 |
| 全部允许模型暂不可用 | 保存retry_wait及最早可重试时间；结束当前派发，下次接续，禁止无限轮询 |

重试只有一个拥有者：StockQA整合现有HTTP/LLM层预算，不能每层各重试三次。价格上限、请求上限和总额对所有备用模型共同生效；未选模型或未设实际预算时可以离线计划，不能启动无上限全池。

故障状态和冷却应跨进程持久化。恢复首选模型要经过冷却和受限健康探测，不能仅凭备用模型成功便认定首选已恢复。新题优先使用已恢复的前序模型，不回头覆盖后序模型已经完成的答案。

不同模型的评分尺度可能不同。保留逐题model、rubric、比较组、原始分数和检查等级；后备模型先参与校准，禁止隐形混分或自动修正成同一尺度。同公司用过多个模型须可见。独立复核与多模型合议只有在单独配置后使用，默认不改变用户要求的顺序执行。

## 5. 各项目的唯一职责

| 对象/动作 | 拥有者 | 其他项目怎样使用 |
|---|---|---|
| 经核验的外部证券身份资料、已有文档原件 | company-wiki | 只读主档/来源契约；没有公司文件夹也不阻止快扫 |
| 研究用实体桥接、长期名单、manual_pin与成员版本 | StockWiki的轻量universe工具 | skill和扫描器通过只读快照/查询使用；没有第二份可编辑名单 |
| 问题内容、类型路由、评分与观察语义 | invest-quick-scan | StockQA加载版本化只读题库或调用现有离线编排工具 |
| 模型配置、API调用、搜索、限流、重试、逐题任务与费用 | StockQAbyLLM | 其他组件提交扫描清单、查询运行状态，不自行重试模型 |
| 已导入的结构化画像、关系、检查、数据集与筛选结果 | StockWiki独立quick_scan库 | 研究技能经只读查询/导出消费，不直接写SQLite |
| 深度预测、情景计算、正式研究资格与报告 | 原有深研skills及StockWiki | 读取快扫线索，按各自契约验证关键事实，不把快扫分数直接当模型参数 |

StockWiki现有runtime jobs可做“启动/查看一次扫描”的外层入口；问答级进度以StockQA为准。页面查询执行器状态，不另复制一套可变重试状态。StockQA执行完成而尚未入库时明确显示“等待导入”。

company-wiki与快扫不是必须串行的采集链。快扫只存问答、来源链接和简短依据；若用户随后深研并需要原件，才走原有来源工作流。没有source_manifest/EvidenceSpan的问答不得伪造它们。

## 6. 两个研究技能怎样使用快扫库

### 6.1 先提供共同的查询契约

建议由StockWiki提供本机只读CLI/查询接口。初期无需先建设远程服务。接口能力如下，均待实施：

| 查询/请求 | 返回内容 |
|---|---|
| capabilities / coverage | 当前是否只有评分、哪些事实域可用，各市场/行业覆盖、新鲜度和词表版本 |
| search_companies | 按细分行业、产品/材料/设备/应用、关系方向和可选评分规则找候选，支持分页和恢复观察 |
| get_profiles | 批量取实体/证券关联、指定字段、证据链接、日期、模型、检查等级、风险与缺口 |
| export_candidate_set | 冻结候选列表、dataset_id、查询参数、关系命中原因和所用观察ID |
| request_refresh | 对指定实体/字段提交有上限的补扫请求，返回请求ID；实际执行仍在StockQA |
| nominate_company / report_discrepancy | 接收池外候选或证据冲突；进入建议/待复核，不覆盖名单或答案 |

每次查询输出都要说明库的覆盖范围。`empty`不等于全市场不存在；`unknown`不等于公司没有这项业务；过期信息可用于线索，但不能默默当当前事实。默认产业检索不要求质量白名单通过，周期低谷及新业务公司也可返回。

查询包固定信息边界、字段版本、入选理由和引用。消费技能可以复用合适的基础描述与候选信息，避免重复问同样问题；关键投资判断和精确模型数字仍按它自己的证据要求处理。LLM问答是候选研究资料，不自动等于正式accepted evidence。

### 6.2 analyze-theme-value-chain

推荐接入位置是“明确主题范围并建立价值链后、搜集与比较公司候选前”。先知道数据库覆盖与术语，再把主题中的细分环节映射到产品、设备、材料与应用关系。

已核对源SKILL：第5步Build the company universe是候选查询入口，第6步Collect comparable company data复用合适的基础字段。原入口明确要求从经济活动拆链，不能从预选股票名单出发，因此先查覆盖能力不等于先让已有公司决定产业链边界。

流程：界定主题/独立构建价值链 → 查快扫库找每一环节候选 → 区分直接生产、上游配套、下游使用、研发探索 → 查看评分与恢复/结构风险 → 对缺口定向搜索或补扫 → 对精选对象做原有增长、估值和受益分析。

必须保留池外发现。主题涉及的环节在库内没有公司时，继续使用原技能研究能力，不能以大池限制整个产业链。新公司可先作为本次候选，长期加入大池则进入nomination；除非用户已明确开启自动加入规则，否则不悄悄扩大全池。

该技能原有主题收入增量、情景预测和比较不能由快扫评分替代。若原工作流要求覆盖特定国家、领导者或完整链条，快扫库是候选和基础事实的复用层，不降低覆盖义务。

### 6.3 industry-research

推荐接入位置是“明确行业框架后、选择公司并采集公司基础资料前”。保持原有行业框架和方法；把其行业/子行业标签与快扫词表建立显式映射，不把近似名称强行当同一行业。

已核对源SKILL：第4步采集行业资料，第6步从框架、wikilinks、companies目录识别和评估公司。计划在第6步加入快扫查询，统一entity_id，按任务截止日/财务期间补缺，不沿用现有公司搜索示例硬编码的2025。没有公司目录也能进入评估。

其PDF输入用于既有行业研究框架，本轮不重写这个框架流程，也不把PDF转换与缓存搬到快扫。公司画像查询本身不要求原件；需要更深证据时由该研究任务按自己的范围处理，不能反向要求快扫为2,000家公司建档。

流程：读取行业框架 → 查库获取同业候选与分类依据 → 对齐经营类型、期间和会计口径 → 复用有效基础信息与相关评分 → 补行业独有问题 → 执行原有行业深入分析。

只复用经济含义、时期和锚点都匹配的分数。行业skill原有评分与IQS分数不默认相等，不把另一个量表换名字即合并，也不把银行/非金融的同名比率直接比较。冲突建立discrepancy记录并继续按独立证据解释，不使用last-write-wins。

### 6.4 补扫预算和回写边界

研究任务查询库本身不产生LLM费用。发现缺口后，默认生成明确的补扫清单；在用户预设的单次实体数、题数、时间和金额额度内可自动补扫，使用同一模型优先级。超出额度则返回未完成项，研究可先用已有结果继续，不自动触发全池重跑。

普通研究任务仅能提名入池、提交补扫和报告冲突，不拥有主库写权限。它自己的结果保持在原研究工件；若未来要采纳某项修正，由快扫校验/导入流程形成新观察，保留来自哪个任务与何种证据。

不制造证据循环：研究报告引用快扫答案，再被快扫当作第二个独立来源，会形成自我确认。需要保留upstream_observation_ids/origin_task，引用原始URL并标明独立性；不能以自己的下游报告给原答案增加置信度。

### 6.5 按当前能力分两步联动

第一步评分库落地后：复用名单、粗分类、评分、风险与恢复观察，帮助缩小研究范围。第二步纯信息题库落地后：增加细分产品/设备/材料/应用关系，才支持较完整的产业链关键词和方向检索。

不能在只有评分的版本宣称“AI硬件全部标的已经可按关系查出”。查询接口要明确facts_available与覆盖率，缺什么就显示什么。
